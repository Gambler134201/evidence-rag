# 成熟 RAG 产品对标与迭代路线（2026-10-25 调研）

> 调研对象：GitHub 上以"产品"形态存在的成熟 RAG 项目（非框架）。目的：提取"成熟"的共性能力层，映射到本项目的迭代路线——**对标不等于抄功能清单**，每项吸收都要回答"这解决了我们评测/用户暴露的什么问题"。

## 1. 对标对象

| 项目 | Stars | 定位 | 对我们的参考点 |
|---|---|---|---|
| [langgenius/dify](https://github.com/langgenius/dify) | 159k | RAG + Agent 工作流平台 | 可观测性、多租户协作、提示词管理 |
| [infiniflow/ragflow](https://github.com/infiniflow/ragflow) | 92.8k | 深度文档理解 RAG 引擎 | 分块可视化人工干预、引用溯源、模板化分块 |
| [QuivrHQ/quivr](https://github.com/QuivrHQ/quivr) | 39.6k | 内容流 → 检索与监控 | 持续摄入、混合检索、格式插件 |
| [labring/FastGPT](https://github.com/labring/FastGPT) | 29.9k | 知识库 QA 平台 | 开箱即用的数据处理链路、可视化编排 |
| [Cinnamon/kotaemon](https://github.com/Cinnamon/kotaemon) | 25.8k | 文档问答工具 | **浏览器内 PDF 高亮引用**、混合检索+重排、低相关警告 |

## 2. 成熟产品的共性能力层

1. **引用溯源的"最后一公里"**：kotaemon 把引用直接高亮到浏览器内 PDF 原文上并附相关分数；RAGFlow 提供 chunk 可视化与人工修正。我们做到了"段落/页码定位 + 相对匹配度"，缺 PDF 原文高亮。
2. **混合检索 + 重排是标配**：kotaemon"hybrid (full-text & vector) retriever and re-ranking"；RAGFlow"multiple recall paired with fused re-ranking"。我们已完成一半（BM25+RRF 已实现），**重排（实验 C）是下一个正当实验**。
3. **低相关警告**：kotaemon 在检索相关度过低时显式警告用户。我们留了 `min_score` 配置位（待开发集校准），前端可低成本加警告条。
4. **分块的透明与可控**：RAGFlow 分块可视化 + 人工干预；我们的文档详情页已有"解析预览"，缺"重新分块/人工调整"操作。
5. **可观测性**：Dify 的执行轨迹；我们 query_runs 已存分段耗时/错误分类/引用快照，缺一个"轨迹查看页"。
6. **反馈与评估闭环**：反馈采集 → badcase 回流 → 回归评测。我们的闭环设计在 S4-T04，feedback 表已建，缺 UI 与流程。
7. **持续集成**：成熟项目人手一份 CI——我们 93 项测试目前只在本机跑。

## 3. 差距分析与取舍（吸收 / 缓做 / 不抄）

| 能力 | 我们现状 | 决策 | 理由 |
|---|---|---|---|
| 混合检索（BM25+RRF） | ✅ 已实现 | — | 首轮 A/B 未显优势，80 条冻结后加权编号题再验证 |
| 重排（实验 C） | 未实现 | **缓做** | 按规划"收益不足则不保留"；冻结集出数后再评估 |

| 引用高亮到 PDF 原文 | 段落/页码定位已有 | **缓做** | 需字形级坐标解析，规划首期排除；MD 文档先做"锚点跳转" |
| 分块可视化+人工干预 | 解析预览已有 | **缓做** | 管理页已有预览，人工重分块等 S2-T06 复用迭代 |

| GraphRAG / OCR / 连接器 / 多步 Agentic 检索 | 未实现 | **不抄** | 规划首期明确排除；除非真实用户问题出现（规划原话） |

## 4. 迭代路线（更新后）

- **阶段 3（当前，等作者复核 80 条草稿）**：冻结 40/40 → 正式 A/B（n≥3）→ 实验 C 重排按需评估 → badcase 回归（smk-07/10 已修）。
- **阶段 3.5 可信工程（新增，对标"成熟开源"底线）**：
  1. GitHub Actions CI：pgvector 服务容器 + 全量测试（本次已落地）；
  2. 运行记录页 + 低相关警告条；
  3. 反馈采集 UI 接入 feedback 表，打通 badcase 回流。
- **阶段 4 产品化（M4/M5 并行）**：用户验证、PDF 锚点跳转、多用户管理界面、流式输出（校验后流式，契约允许）。
- **明确不抄**：GraphRAG、OCR、网页连接器、多模态解析、多步 Agentic 检索——除非真实用户问题或评测结果证明需要（原规划 §3 原话，这也是与"功能清单式产品"拉开差距的地方）。

## 5. 简历价值标注

## 6. 迭代方案与步骤（2026-10-25 详化为可执行计划）

> 排序原则：先用**已有数据**产出产品能力（阶段 A，零新依赖），再做**数据驱动的检索迭代**（阶段 B，冻结 dev 集现在可以合法调参了），然后补**引用最后一公里**（阶段 C），最后是**产品化门面**（阶段 D）。每步给验收条件（沿用 AUTO/FILE/MANUAL 标签）与工作量（S<半天 / M 1~2 天 / L 3 天+）。刻意不排的：GraphRAG/OCR/连接器/Agentic 多步检索（见 §4 不抄清单）。

### 阶段 A：把已有数据变成产品能力（零新依赖，先做）——A1 已于 2026-10-25 完成

| 步骤 | 内容 | 验收条件 | 量 |
|---|---|---|---|
| **A1 拒答阈值校准 + 低相关警告** | 用冻结 dev 集校准 `min_score`（S1-T07 留的配置位终于有数据了）：扫描 dev 40 题的证据分数分布，选定"低于此分必拒答"阈值写入配置；前端对低于阈值/零证据的回答显示"证据相关度较低"警告条（对标 kotaemon low-relevance warning） | `AUTO`：dev 集上阈值扫描报告（各阈值下的拒答正确率/误拒数）；`MANUAL`：前端警告条可见 | S |
| **A2 运行记录页（轨迹查看器）**（✅ 2026-10-25 完成：列表/详情/证据预览/原文跳转，94 项测试） | 四类页面缺的最后一块：列表页（query_runs 分页）+ 详情页（问题/六态/分段耗时/引用与片段快照/错误分类），失败题一键跳转证据。m36/m57 类失败从"翻 raw.jsonl"变成"页面上看" | `AUTO`：接口经授权过滤（非本人 404）；`MANUAL`：从管理页可打开任一次运行详情 | M |
| **A3 反馈闭环 UI** | 回答页加"有用/无用 + 原因"按钮（写 feedback 表，表已建）→ 管理页"反馈清单" → 无用反馈按六类预归因 → 回流清单进入下一轮评测候选。对标 Dify/kotaemon 的反馈闭环，也是 S4-T04 的提前落地 | `AUTO`：反馈写入与查询接口测试；`FILE`：回流清单生成；`MANUAL`：无用反馈能在管理页看到 | M |

**阶段 A 出口**：三次使用"已有数据"的能力上线；m69（过度拒答）经 A1 阈值直接改善；badcase 从"事后翻日志"变为"页面即时可见"。

### 阶段 B：数据驱动的检索迭代（✅ 2026-10-25 完成：B1 归因 18 条、B2 扫描、B3 重排实验——见下表与 evals/results/phase-b-experiments.md）

| 步骤 | 内容 | 验收条件 | 量 |
|---|---|---|---|
| **B1 失败题归因分析**（✅ 18 条系统性失败：R2×5、G*×9、R1×2 为设计性、混合特有×2） | 对正式 A/B 的系统性失败题（m36 检索不足、m57/m58/m19/m21 模式特定、m04）逐题做 R1/R2 判定（top-20 候选已存），产出归因报告：R1（检索真没有）→ 改分块/加查询扩展；R2（在候选没进 top-5）→ 重排/调融合；G 类 → 生成侧 | `REVIEW`：每题归因 + 证据（候选命中位置），挂到 `docs/optimization-log.md` | S |
| **B2 调参扫描** | 依据 B1：在 **dev 40 题**上扫描 top_k（3/5/8）、candidate_k（10/20/40）、RRF k（40/60/120）、分块参数（300/500/700），产出参数敏感性报告；**留出集一次性验证**胜出配置 | `REVIEW`：dev 扫描矩阵 + 留出集一次验证（不反复触碰） | M |
| **B3 实验 C：重排** | 硅基流动 `BAAI/bge-reranker-v2-m3`（同账号已开通，免费档）接 rerank 通道（`retrieval_mode=rerank`），在 dev 集对比 Recall@5/通过率/时延增量；收益不足则记录"不做"决定（对标 kotaemon/RAGFlow 的 fused re-ranking） | `REVIEW`：dev 对比报告（重排前后 Recall@5 与时延增量）；`MANUAL`：保留与否的决策记录（规划要求"收益不足则不保留"） | M |
| **B4 查询扩展（轻量）** | 对 R1 类失败（m36）：检索前用生成模型做一次查询扩展（同义改写/拆分子问题），仅在向量模式 Recall 不足时触发；**不引入多步 Agent 循环**（红线） | `REVIEW`：R1 失败题修复率对比报告；不修复则记录原因 | M |

**阶段 B 出口**：留出集 Recall@5 从 81.0% 向 85% 门槛推进的量化记录；每个参数变化都有 dev/留出分离的实验证据——这就是简历上"基于归因的检索优化迭代"的完整素材。

### 排序与依赖

```
A1 → A2 → A3（阶段 A，互相独立可并行，共约 3~4 天）
B1 → B2 → B3 → B4（阶段 B，依赖冻结 dev 集合法调参，共约 4~6 天）
C1（依赖前端证据交互，可插在 A/B 之间）
```

**指标目标（阶段 B 出口）**：留出集 Recall@5 81.0% → ≥85%（规划门槛），稳定通过率 92.5% → ≥95%；每一分提升都有 dev/留出分离的实验记录。达成后简历句式升级为"通过归因驱动的检索优化，将 Evidence Recall@5 从 81.0% 提升至 8X%"。

### 仍然不做的（红线重申）

GraphRAG、OCR、网页连接器、多模态解析、多步 Agentic 检索循环、微服务拆分、计费系统。任一项引入需先由用户与主脑确认，并追加带理由的变更条目。

## 7. 阶段 E：规模验证（2026-10-25 新增，回答"要不要换真实大规模知识库"）

> 拆分两个被混在一起的问题：**评测质量**（当前冻结集 80 条 + 153 条款语料负责）与**工程规模**（真实大规模知识库负责）。前者换语料 = 评测作废重考；后者不动评测，只压测工程栈。结论：现在不换语料，但补一个独立的规模验证阶段。

### E1 规模压测（公开语料，不碰私有资料红线）

- 用**公开语料**（开源项目文档、公开法规全文等，无版权/隐私问题）灌 1k → 5k → 20k chunk 到**独立知识库**（kb-scale），与演示库隔离；
- 实测三条曲线：精确向量检索 P50/P95 随 chunk 数的变化；内存 BM25 的容量与耗时上限（当前实现 `corpus_limit=5000`，超限即到边界）；worker 批量入库吞吐；
- 产出：**规模-延迟曲线 + ANN 触发决策记录**——原规划"数据量和延迟上来再考虑 ANN 索引"的触发条件第一次被真实测试，简历上多一条"实测精确检索到 N chunk 后延迟拐点，切换 HNSW"的工程叙事。

### E2 BM25 通道的规模改造（E1 结果驱动）

- 内存 BM25 在万级 chunk 不可持续；pgvector 同库的自然路径是 **PostgreSQL 全文检索（tsvector + GIN）**替代内存 BM25——中文分词仍用 jieba 预处理，RRF 融合逻辑不变；
- 验收：`AUTO` 万级 chunk 上关键词检索 P50 对比报告；`MANUAL` 是否切换的决策记录。

### E3 真实私有资料（红线不变）

- 按原规划：**M4 用户验证完成 + 权限体系经真实使用检验后**才接入私有资料；届时"换库"只是数据操作（管理页上传/发布/停用），架构零改动——这也是版本与权限设计的回报。

### 排序

E1/E2 在**阶段 B（Recall 85% 冲刺）之后**执行——理由：阶段 B 的调参实验绑定当前冻结集，中途换语料会让调参基线作废；且规模验证不影响评测质量指标，两者互不阻塞。私有资料接入排在 M4 后（红线）。
