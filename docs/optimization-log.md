# 优化迭代记录（case study 素材：失败 → 归因 → 修复 → 回归）

> 本文档记录有完整证据链的优化迭代。每轮：失败现象 → 六类归因 → 修复 → 同口径回归。
> 所有数字来自真实运行（`evals/results/` 下原始记录可复跑），数据集为作者复核转正的冒烟集（10 条，smk-05 权限占位）。

## 迭代 1：G2 badcase 修复（提示词契约 v1 → v2.1，2026-10-24）

### 失败现象（修复前，contract-v1）

| 题 | 预期 | 实际 | 六类归因 |
|---|---|---|---|
| smk-07「整改必须在几个工作日内完成？」 | refuse（资料明确"不另设整改天数"） | answered——内容正确（"没有统一天数"）但形式错误 | **G2**（应拒答却回答） |
| smk-10「对方多久不回复能登记人工协调？」 | needs_clarification（A 用工作日/B 用自然日，须先确认团队） | answered——直接给了 A 的天数 | **G2**（应澄清未澄清） |
| smk-03「2026-09-15 的提交验收期几天？」 | needs_clarification | 跨运行不稳定：一次 clarify（对）、一次直接用现行天数（错） | **G2**（间歇性） |

两轮基线（vector 7/9、hybrid 6/9）中 smk-07/10 均稳定复现——系统性问题，非波动。

### 归因

检索侧无责（金标锚点全部命中 top-5）。生成侧：契约提示词 v1 的"缺必要条件 → 澄清"规则太弱，模型把"内容正确"当"形式正确"。

### 修复（三轮提示词迭代，每轮同口径回归）

| 版本 | 修改 | 回归结果 | 教训 |
|---|---|---|---|
| contract-v1 | — | 7/9（smk-07/10/03 失败） | 基线 |
| contract-v2 | 增加硬规则 6（无依据必须拒答、不得包装成 answered）+ 7（数值依赖未确认前提必须先澄清） | 8/9——**smk-07/10 修复，但 smk-02 被误伤**（问题已指明"A 团队"，模型仍追问归属） | 新规则过宽，产生过度澄清 |
| contract-v2.1 | 规则 7 收紧：前提**已能确定时不得追问**（问题点名对象/调用者所在库即适用范围/证据写明适用对象） | **9/9 全过**，smk-02 恢复、smk-07/10/03 保持通过 | 规则要配"反向豁免"，否则修 A 坏 B |

### 证据

- 修复前：`evals/results/ab-vector/raw.jsonl`（7/9）
- 迭代过程：`evals/results/iter1-g2fix/`（8/9）、`evals/results/iter2-v21/`（9/9）
- 配置快照：各目录 `config-snapshot.json`（prompt 版本已入快照，可复现）
- 回归方式：`ENABLE_REAL_MODEL_CALLS=1 python evals/tools/run_eval.py --dataset evals/datasets/smoke-10.jsonl --mode vector --name <名称> --skip-ingest`

### 面试表述（要点）

"冒烟集暴露 2 个稳定 G2 badcase：模型把'内容正确'当'形式正确'——资料说没规定的事，它引用着证据给一段 answered。归因到生成侧后改提示词契约，第一版规则过宽把已指明团队的问题也拿去追问了，收紧加反向豁免后 9/9。整个过程三次回归都是同数据集同口径一键复跑。"
