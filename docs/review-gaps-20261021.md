## 1. 【最高优先级】语料太小太干净，评测会失去区分度

**问题**：现在 5 份文档、约 20 个条款。检索 top-5 相对 20 个候选，等于在 25% 的语料里挑。向量检索的 Evidence Recall@5 很可能直接接近 100%。

**后果**：`implementation-plan.md` 里 A/B/C 三组对照（纯向量 → +BM25 → +rerank）**测不出差异**，最后三行数字都是 95%+，评测没有信号，简历上「命中率从 X 提到 Y」也拿不到。而且 ≥85% 的门槛在 5 份文档上是**白送的**，面试官一问「语料多大」就露。

**具体补法**（在 M1 检索基线**之前**做，不是阶段 3）：

1. **加干扰知识库**，语义近邻但答案错误：
   - `kb-c` 外包交付规则：同样讲「工作日」「验收」「提醒」，但期限是 4 个工作日、提醒后 1 个工作日
   - `kb-a` 的 **v3 草案**（`status: draft`，未生效）和一份 **v2.1 废止版**（`status: deprecated`）
   - 一份「验收流程培训讲义」，复述规则但措辞不同、数字写错（教学样例）
2. **加近似改写段落**：同一条规则在 FAQ、手册、讲义里以不同措辞出现 3–4 次，向量会把它们全召回来抢 top-5
3. **规模目标**：条款数从 ~20 提到 **150–250**，其中至少 30% 是语义近邻干扰

**验收标准**：纯向量基线的 Evidence Recall@5 落在 **60–85%** 区间。如果 >90%，说明干扰不够，继续加——**基线太高的评测集是废的**。

## 2. 日期/工作日题会污染指标，必须单独归类

**问题**：A-F-02 那种「2026-10-16 提交，截止哪天」是**推理题**，不是检索题。LLM 算工作日极易错（跨月、节假日、端点含不含），失败原因跟检索质量无关。混进「可回答问题通过率 ≥75%」里，你会误判成检索退化。

**补法**：
- 评测集加 `type: reasoning` 一类，**不计入 Evidence Recall**，单列「计算类正确率」
- 要求系统输出计算过程（引用 A-D2-02 + 列出工作日序列），只给最终日期不算通过
- 在 README 明确写：「计算类失败归入生成/推理，不归入检索」——这句话本身就是加分项

顺带：`A-D2-02` 的「次一工作日起 3 个工作日」「截止为最后一日 18:00」是**端点歧义**高发点。建议专门放 2 条边界题（第 3 个工作日当天 18:00 整回复算不算逾期），并在评测集里注明「本演示未定义，系统应说明未定义而不是猜」。

## 3. 缺 badcase 归因分类：只有数字，没有归因

**问题**：指标从 82% 掉到 71%，你下一步做什么？没有归因分类，数字下降无法行动。

**补法**：固定 6 类，每条失败必须归一类（已写成 `evals/badcase-taxonomy.md`）：

```
R1 检索未召回（正确片段不在候选里）
R2 召回但排名低（在候选里但没进 top-5）
P  权限/版本过滤错误（正确片段被过滤掉，或错误版本被放行）
G1 生成未依据上下文（上下文里有正确证据，答案仍错）
G2 应拒答却回答（无依据仍作答）
G3 引用不支持（引用了，但引用内容不支持结论）
```

**面试价值**：被问「你怎么定位问题」时，能报出归因分类和「上周 R2 占 40%，所以我加了 rerank」这种因果链，比报任何指标都强。

## 4. 格式夹具不该推到「以后」——真实文档的难处是面试必问

**问题**：`data-plan.md` 第 5 节把 TXT/文本 PDF 夹具推到「以后单独建立」，扫描 OCR、复杂表格不在首期。但你的语料全是**干净 Markdown**，等于回避了企业 RAG 80% 的真实难度。面试官一定会问「真实文档有 PDF、表格、页眉页脚，你怎么办」。

**补法**：M1 就加 3 份格式夹具，**不实现 OCR**，但要求解析器 **fail-loud**：

| 夹具 | 考点 |
|---|---|
| 文本 PDF，含**跨页表格** + 页眉页脚 | 页眉会不会污染 chunk；表格跨页后参数和表头会不会分离 |
| TXT，异常换行 + 全角半角混排 + BOM | 规范化策略；会不会把条款编号切坏 |
| 扫描图 PDF（无文本层） | **解析器必须报错并记录，不能静默跳过** |

我已经在 `examples/format-fixtures/` 放了一份带跨页表格和页眉页脚的 PDF 夹具（含生成脚本），你可以直接用。

**「我的解析器不会静默丢内容，无法解析的页会显式失败并记录」**——这句话是很强的工程卖点，而且和你「不采信自述、只接受可验证结果」的原则完全一致。

## 5. 金标核对缺记录格式

**问题**：你写了「不能把执行模型自评称为人工金标」，很好。但缺一张核对记录：谁核对、什么时候核对、文档修订后锚点有没有复核。没有这张表，「人工金标」这四个字在面试里守不住。

**补法**：见 `evals/badcase-taxonomy.md` 第 3 节的核对表模板。要点：
- 每条 gold 记「核对人 / 核对时间 / 锚点原文摘录 / 是否随文档修订复核过」
- 你自己核对的条目要标 `reviewed_by: author`，**不要写成「人工核对」暗示有第二人**——面试官会问「谁核对的」，诚实比好看重要

## 6. 缺「上线后」设计（面试高频，且你项目 01 有现成素材）

**问题**：`implementation-plan.md` 覆盖到评测和验收，但没有「上线后怎么持续监控」。必问：「上线之后效果变差你怎么发现？」

**补法**（写进 plan 的 M4，不用实现）：最小 badcase 回流闭环
```
用户点「引用不支持结论」 → 进入待复核队列（带 query、候选、引用、答案）
→ 人工复核归因（用第 3 节的 6 类）→ 确认的 badcase 加入评测集（进留出集，不进开发集）
→ 下一轮评测自动包含
```
再补三个线上最小指标：无答案率、拒答率、引用缺失率的**周环比**（不需要 APM，一张表就够）。

你项目 01 里已经做过「关键操作留痕」「先审后展示」——把这套思路迁移过来，叙事是连贯的。

## 8. 你最大的资产没写下来：三个项目是一条线

你的三个项目其实互相咬合，但仓库里没有任何地方说明：

```
需求集市（项目 01）
  └─ 业务规则、验收状态机、权限模型  ──→  evidence-rag 的合成语料就是它的规则文档
multi-agent-collaboration（项目 02）
  └─ 主脑定验收条件、不采信执行器自报、独立验收、单次整改上限
        ──→  你现在就是用这套方法开发 evidence-rag（.model-desk/runs/*/review.json 是物证）
evidence-rag（项目 03）
  └─ 评测先行、gold 锚点不可变、fail-loud 解析、权限与版本门禁
```

**面试就这么讲**：「我做第三个项目时，用的是第二个项目里那套机制——先写可判定的验收条件，再让执行模型实现，我不采信它自报的『做完了』，只跑评测和门禁。第一个项目的业务规则正好成了第三个项目的语料。」
