# 案例复盘（case study，骨架 + 真实素材）

> 按原规划 §10：作品需含"一次产品取舍 + ≥3 个失败案例及修复前后对照"。本文汇集 2026-10-24 单日开发中的真实素材；简历与面试只引用文中有证据链的部分。

## 1. 产品取舍：引用编号由谁生成

- **背景**：引用可溯源是本项目第一卖点，但模型可能编造文档 ID。
- **备选**：让模型自由输出文档 ID / 模型只输出局部编号 C1..Cn，由服务器补全真实来源。
- **选择**：后者。程序校验"编号 ⊆ 本次送入模型的证据集合"，编造即整体拦截（citation_invalid），绝不"删标记后照发正文"。
- **影响**：提示词必须给编号化证据；前端引用展示由服务器载荷驱动。
- **依据**：`services/api/evidence_rag/rag.py`（契约与拦截）、`test_rag.py` 编造引用测试。

## 2. 失败案例 1：G2——"内容正确"不等于"形式正确"

- **现象**：资料明确"不另设整改天数"，模型却引用该条款给一段 answered；问"多久不回复能登记"不确认团队归属直接给天数。
- **归因**：六类归因 = G2（应拒答/应澄清却回答）；检索无责（锚点全命中 top-5）。
- **修复**：契约提示词三轮迭代（v1 → v2 增拒答/澄清硬规则 → v2.1 加"前提已确定时不得追问"的反向豁免），同数据集回归 7/9 → 8/9 → **9/9**。
- **证据**：`docs/optimization-log.md`、`evals/results/ab-vector|iter1-g2fix|iter2-v21/`。

## 3. 失败案例 2：机械指标会冤枉检索——口径先行

- **现象**：smk-03（历史提交适用规则）金标锚点不在检索结果里，机械 Recall 记为未命中。
- **真相**：历史版本**未发布是设计行为**——该题预期就是"先澄清历史访问范围"，检索没犯错。
- **修复**：不是改检索，是改口径：该题归澄清类、不计 Recall 分母（作者复核决定，见 `evals/gold-review.md`）。
- **教训**：指标下降先做归因，别急着调检索——"口径区分"本身就是评测设计的一部分。

## 4. 失败案例 3：基础设施的三次"自证"

1. 不可变触发器拦下了入库代码自己的 storage_key 后补更新 → 设计改为"先定稿再建行"；
2. 迁移在全新测试库上失败（vector 扩展未建）→ 迁移自带 CREATE EXTENSION，测试体系首轮运行即抓到真 bug；
3. 前端 kb 页操作按钮 fetch 少拼 API_BASE——手动走查（MANUAL 验收）抓到，AUTO 断言抓不到。

## 5. 评测设计发现（超出预期的收获）

- **思考型模型稳定性**：温度 0 下同一题跨运行状态仍会漂移（smk-03 clarify↔answered）→ 正式评测每题 n≥3、稳定性单列指标；
- **BM25 负 IDF**：标点 token 在小语料产生负 IDF 拖垮整句得分 → 切词过滤纯标点；RRF 只依赖相对排名；
- **跨库数值巧合**：kb-c 与 kb-a 期限数值相同、kb-b 外包与 v2.1 相同——语义近邻干扰设计在真实检索中确实制造了混淆风险。
