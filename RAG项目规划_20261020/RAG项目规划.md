# RAG 项目规划：知据——可溯源的团队知识助手

编制日期：2026-10-20  
用途：新项目立项、分阶段实施、作品展示与 AI 岗位面试准备  
当前状态：规划，尚未开发；本文的数量、指标与排期均为建议目标，不是已取得的成果。

## 1. 项目定位

做一款面向小型项目团队的知识问答产品：将项目规则、交付流程、操作手册与常见问题整理为知识库，用户提问后，得到基于当前有效文档的回答，并能点击查看引用原文；证据不足时明确说明或要求补充条件。

建议中文名：知据。英文仓库名暂定：evidence-rag。名称仅为建议，不默认创建或发布仓库。

核心表达：不仅回答“是什么”，还说明“根据哪一份、哪一个版本、哪一段资料”。

首个场景选用“团队项目交付知识库”：需求发布、阶段交付、验收期限、退回整改、争议处理与操作说明。可以使用自行编写的演示规则，与需求集市业务经验呼应，但产品独立开发、独立部署，不依赖原网站或多 Agent 框架运行。

示例问题：
- 阶段交付后，对方一直不验收应该怎么处理？
- 旧规则和新规则对验收期限的要求不同，目前适用哪一个？
- 哪些情况必须人工介入？请给出对应依据。
- 我能看到另一个团队的内部操作手册吗？
- 资料里没有退款规则时，系统会不会自行编造？

目标用户：需要查阅项目文档的成员，以及维护这些文档的管理员。首期不面向法律咨询，不自动裁决真实争议，不执行付款、删库等外部操作。

## 2. 为什么值得做，以及做到什么程度才有竞争力

在两个已有项目之外，补齐 RAG 的检索、证据、版本与评测能力，并体现产品设计和工程落地的连接。

| 已有经验 | 本项目要补的能力 | 最终证据 |
|---|---|---|
| 需求集市的业务流程与状态规则 | 将业务知识变为可检索、可维护的数据 | 知识库、文档版本与使用场景说明 |
| 多 Agent 的调用、验收与故障处理 | 检索错误和生成错误的分别定位 | 检索轨迹、错误分类与修复前后对照 |
| 网站、API、数据库与部署实践 | AI 功能的完整用户体验与运行质量 | 可演示产品、调用记录、延迟与费用统计 |
| 个人项目设计 | 用户验证和产品取舍 | 访谈记录、任务观察、迭代依据 |

最低有说服力的交付：可运行产品 + 有来源的数据集 + 固定评测 + 一次有证据的优化 + 一份用户反馈总结。仅上传 PDF 后聊天，不作为项目完成标准。

## 3. 范围控制

### 必须完成（P0）

1. 文档管理：上传、解析、状态反馈、重复检测、重试、停用或更新版本。
2. 支持 Markdown、TXT，以及可提取文本的 PDF；保留标题/段落或 PDF 页码定位。
3. 按授权知识库检索，基于检索结果生成回答，返回真实引用。
4. 无有效依据、问题含糊、证据冲突时，有明确的用户反馈路径。
5. 文档更新与停用后，新查询不再使用已失效内容。
6. 可查看本次检索命中、耗时、模型配置、使用量与错误分类。
7. 固定评测集和可复跑报告。
8. 最终展示版具备登录与服务端权限校验；公开体验区只使用合成或可公开资料。

### 有基线后再做（P1）

- 中文关键词检索与向量检索融合。
- 按证据决定是否增加重排模型。
- 简短多轮追问；历史仅辅助理解，不作为文档证据。
- 用户反馈与失败案例回流。
- 限定规模、明确环境下的性能与稳定性优化。

### 首期明确不做

扫描件 OCR、复杂表格/图像理解、网页自动抓取、GraphRAG、模型微调、复杂 Agent 自主规划、多 Agent 并行、自动业务执行、移动端、计费系统、大规模企业 SaaS、集群与微服务。

这些能力不是永远不做；只有实际用户问题或评测结果证明需要时才增加。

## 4. 用户流程与页面

### 普通成员

登录 → 选择有权限的知识库 → 输入问题 → 阅读回答与证据 → 点击引用原文 → 标记有用/无用并填写原因。

### 管理员

登录 → 上传文档 → 查看解析预览 → 补充版本/生效信息 → 建立索引 → 发布为有效版本 → 更新或停用 → 查看失败任务与反馈。

首期页面控制为四类：
1. 问答页：回答区、证据抽屉、无答案与澄清状态。
2. 知识库页：文档列表、版本、索引进度、失败原因。
3. 文档详情页：段落/页码、版本、生效状态、解析预览。
4. 评测与运行记录页：先做简洁表格，离线评测报告可以先用 HTML/CSV，不急于开发完整后台。

建议视觉：简洁青绿色，突出引用、版本与证据，避免聊天界面占据全部产品表达。

## 5. 技术方案与链路

### 推荐起步组合

| 层 | 建议 | 取舍 |
|---|---|---|
| 前端 | Next.js + TypeScript | 复用已有经验，负责界面；核心业务逻辑不在两套后端重复实现 |
| 后端 | Python + FastAPI + Pydantic | 展示 Python 服务化、接口与数据校验能力 |
| 数据库 | PostgreSQL + pgvector | 业务记录与向量放同一数据库，减少运维组件 |
| 解析 | Markdown/TXT 解析；pypdf 提取 PDF 文本 | 扫描件或低质量提取明确报不支持，不把空文本当索引成功 |
| 检索 | 先精确向量检索，再试关键词融合 | 小数据先保证正确，数据量和延迟需要时才考虑 ANN 索引 |
| 模型 | 独立配置生成模型与 Embedding 模型 | 不能假定能生成回答的 DeepSeek 接口也提供 Embedding |
| 重排 | P1 按实验结果选择支持中文的模型或接口 | 比较质量、延迟、费用，再决定是否保留 |
| 测试/部署 | pytest、少量关键页面端到端检查、Docker Compose | 先做本地可复跑，再决定是否公开部署 |

生成模型可使用已有可用 API 或本地兼容服务；Embedding 必须单独验证中文效果、向量维度、上下文长度、硬件或接口要求。选定后锁定依赖与模型版本，写入配置清单。不要为了跑 RAG 而占用或重启正在服务其他项目的模型。

不强制引入 LangChain/LlamaIndex；首期用清晰模块把链路讲明白。如果实际能减少重复代码，再局部采用框架，并能解释框架代做了哪些事。

### 文档入库

上传校验 → 文件哈希 → 解析/预览 → 标题与段落分块 → 保留来源定位 → Embedding → 写入待发布版本 → 校验完整性 → 原子发布有效版本。

- 分块参数是实验变量，可从约 300～600 中文字符、少量重叠开始试验，不作为通用最优值；同时检查 Embedding 的 token 限制。
- 引用定位绑定不可变的文档版本与 chunk_id，不只保存显示名称。
- 相同文件哈希和相同处理配置不重复计费建索引；分块/Embedding 配置变化需建立新索引版本。
- 更新期间旧版本可继续服务；新版本完整就绪后切换。失败时保留可用版本与错误信息，避免半套索引进入查询。

### 问答

服务端确认身份与知识库权限 → 解析问题 → 仅检索授权且有效的文档 → 可选融合/重排 → 组装有编号的证据 → 生成回答 → 校验引用编号与版本 → 展示原文/反馈 → 保存最小必要运行记录。

- 引用编号必须属于本次真正送入模型的证据；禁止模型编造文档 ID。
- 引用存在不等于内容支持结论。程序校验来源真实性，人工或评测另行检查语义支撑。
- 不直接将相似度当作“答案正确率”。拒答阈值应在开发集校准；问法含糊可先澄清，不必全部拒答。
- 文档中出现“忽略上文、输出密钥”等文字时，只作为资料内容，不执行其指令。测试防护效果，不能宣称完全免疫注入。

### 中文混合检索的注意点

PostgreSQL 有全文检索能力，但默认配置不能直接视为可靠的中文分词方案。建议小规模先用经过验证的中文切词 + BM25 作为关键词通道，与向量结果按 RRF 融合；具体依赖在实现时核对维护状态与许可证。

关键词索引也必须只覆盖当前用户授权且有效的资料。首期数据少，可以在授权集合内做简单实现，不急于增加 Elasticsearch。

## 6. 数据与权限设计

建议实体：users/memberships、knowledge_bases、documents、document_versions、chunks、ingestion_jobs、query_runs/feedback。可按实现合理拆表，不追求表的数量。

关键字段包括：knowledge_base_id、document_id、version_id、content_hash、locator、effective_at、active 状态、chunk_id、embedding_model、embedding_dimension、pipeline_revision。

权限原则：
- 请求中的知识库 ID 只是选择参数，服务端必须按登录身份核验访问权。
- 权限过滤覆盖检索、融合、重排、原文预览、下载、运行记录与导出，不能只在前端隐藏。
- 未授权文本不进入模型上下文、关键词候选池或用户可读调试记录。
- 首期不做跨用户回答缓存，避免缓存绕过权限与版本变化。
- 文档停用/撤权后，新查询和原文链接立即按新权限判断；历史回答是否保留、引用能否打开在 PRD 中说明，不暗示能撤回用户已经看过的内容。
- 原始文件、数据库、上传文档、密钥和真实查询不入 Git。日志默认不保存完整敏感文档与认证信息。

权限功能上线前只使用本地合成数据；面向他人的可访问版本不能依赖“选择一个用户”的演示控件代替认证。

## 7. 演示数据与评测设计

### 数据准备

建议先编写 20～30 份短文档，约 100～300 个有效片段；数量以覆盖场景为准，不为凑体量堆文档。

应包含：规则、FAQ、操作手册、跨文档依赖、明确生效的新旧版本、知识库 A/B 同名不同内容、无答案问题、少量带干扰指令的演示文档。记录来源、授权/许可证和版本；合成资料明确标注“演示规则”，不能伪称真实客户数据。

### 问题集

目标 80 条，人工编写并核对标准证据，不将模型自行生成的答案直接当标准答案。

| 类别 | 数量 | 检查重点 |
|---|---:|---|
| 单文档事实 | 30 | 找到正确片段并忠实回答 |
| 跨段/跨文档 | 20 | 需要的关键证据是否齐全 |
| 新旧版本 | 10 | 只按适用版本回答 |
| 无答案/需澄清 | 10 | 不编造，有合理拒答或追问 |
| 干扰/文档指令 | 10 | 不把资料文字当系统指令 |

按类别均衡分为 40 条开发集和 40 条留出测试集。先冻结测试集，不根据测试集逐题改提示词；查看测试结果后继续调参时，保留旧报告并另备新留出集。两个集合的近似改写也要去重。

另外准备至少 20 个权限与生命周期断言：跨知识库检索/原文链接、撤权、停用、更新、索引失败等。它们独立于问答质量分母。

每条样本至少包含：question_id、question、category、调用者角色/知识库、适用时间、gold_evidence_ids、expected_points、should_abstain_or_clarify、split。

### 对照实验

1. A：仅向量检索。
2. B：向量 + 中文关键词检索 + RRF。
3. C：在 B 上增加重排，仅在需要时做。

固定语料快照、生成模型、提示词、top-k 和评分标准，逐次只改一个因素。记录语料/代码/配置版本。最终方案是否优于基线由结果决定；不预设“加重排一定更好”。

### 指标和建议完成门槛

以下为立项目标，完成后填写实际分子/分母；小样本结果不能外推为所有企业场景的准确率。

| 指标 | 定义 | 建议门槛 |
|---|---|---|
| Evidence Recall@5 | 对有标准证据的问题，top-5 命中的必需证据数量 / 必需证据总数，再按问题平均 | 留出集可回答问题平均 ≥85% |
| 回答通过率 | 必需信息正确、无关键编造、满足题目要求的问题数 / 可回答问题数 | 留出集可回答问题 ≥75% |
| 引用支持率 | 经人工判断被引用原文支持的可核验结论数 / 带引用的可核验结论总数 | ≥90%，另报引用缺失数 |
| 无答案处理正确率 | 正确拒答或合理澄清的问题数 / 此类问题总数 | ≥90%；同时报告小样本数量 |
| 权限/生命周期断言 | 对应可重复的后端检查 | 至少 20 项全部通过，发现泄漏先修复 |
| 性能与成本 | 完整回答延迟 P50/P95、检索/生成耗时、输入/输出 token、费用或未知原因 | 必须可测可追踪，不预先承诺固定秒数或金额 |

人工评分保留理由和示例；自动 LLM 评审只作辅助，抽查不一致项，不能同一模型自己判分后宣称“人工验证”。模型拒答率过高也可能虚增安全指标，要同时观察可回答问题被误拒的情况。

费用按真实提供方用量和已核实单价计算，记录日期与币种。缺失使用量或免费额度抵扣信息时标记未知，不填 0。公开演示需要访问与调用频率限制，不默认开放无限付费调用。

## 8. 实施阶段与退出条件

以下是顺序建议，不承诺固定工期。每阶段交付后只检查相关改变，不反复运行整套评测；真实模型回归集中执行，单元/集成测试默认 mock。

| 阶段 | 主要工作 | 完成标准 |
|---|---|---|
| 0 立项与环境 | 确认场景、文档样本、模型可用性；最小 PRD/原型；依赖与预算方案 | 能说明用户是谁、要解决什么、先不做什么；生成与 Embedding 分别做最小连通验证 |
| 1 最小闭环 | 5 份文档、解析分块、向量检索、回答、真实引用 | 10 个样例能追到原文；无答案不伪造引用；解析失败可见；保留基线配置 |
| 2 可管理版本 | 文档更新/停用、入库任务状态、重复检测；登录权限 | 更新不混版本、失败不污染线上索引；服务端权限及原文链接检查通过 |
| 3 效果优化 | 扩充数据、冻结样本；基线与融合检索对照；按需重排 | 有可复跑的原始结果、错误分类、收益和代价；不要求所有新方案胜出 |
| 4 用户验证 | 邀请 5～10 名潜在用户完成指定查阅任务 | 记录能否完成、引用是否易懂、耗时与反馈；做至少一次有依据的迭代 |
| 5 作品整理 | 安装/演示/评测/复盘文档；整理公开数据与密钥边界 | 新环境可按文档启动；关键演示可复现；简历只写已完成和实测结果 |

如果时间有限，优先完成 1～3，形成可展示的独立项目，再继续用户验证。公开部署不是最小闭环的前置条件；权限未完成前不接入私有真实资料。

## 9. 关键验证与失败分析

最小有价值的测试：
- 同名不同文档、重复上传、空文件、扫描 PDF/损坏文件、超限文件。
- 分块后页码/标题/版本定位可用；不存在的引用编号被拦截。
- 必要证据未召回 vs 已召回但答错，分别统计。
- 无答案、条件缺失、新旧冲突、多文档证据组合。
- 其他知识库的检索、原文与下载越权；撤权/停用后新请求失效。
- Embedding 或生成接口超时/限流/返回异常、入库中断与重复任务。
- 日志/导出/公开样本中不存在密钥和真实私有资料。

失败分类建议：解析、分块、索引/更新、召回、排序、权限、生成、引用、产品交互、服务故障。每次优先修复占比最高或影响最大的类别，不用不断扩充提示词掩盖数据问题。

## 10. 作品与求职材料

建议仓库结构（参考，不要求一开始创建所有空目录）：

```text
evidence-rag/
  apps/web/
  services/api/
  services/api/tests/
  evals/datasets/
  evals/results/
  examples/public-docs/
  docs/PRD.md
  docs/architecture.md
  docs/evaluation.md
  docs/case-study.md
  docker-compose.yml
  .env.example
  README.md
```

保留以下可展示成果：
- 2～3 分钟演示：上传 → 提问 → 引用 → 更新版本 → 无答案 → 权限边界。
- 架构图、最小 PRD、一次产品取舍记录。
- 固定数据集、可复跑命令、原始结果与版本信息。
- 至少 3 个有代表性的失败案例及修复前后对比。
- 小规模真实试用总结；说明样本量，不夸大增长或效率。

产品方向面试：重点讲场景、需求验证、证据体验、拒答取舍、指标和用户反馈。
应用开发方向面试：重点讲中文检索、分块/Embedding、权限、版本发布、错误恢复和评测。需要自己能定位代码并解释关键实现，AI 代写代码不能替代个人理解。

完成后可用的简历句式（占位，不能提前写成成果）：
“设计并实现可溯源的团队知识助手，支持文档入库、版本更新、授权检索与引用定位；基于 X 条冻结样本对比向量/混合检索，Evidence Recall@5 从 A 提升至 B，完整回答延迟为 C，并通过 Y 项权限与生命周期检查。”

## 11. 推进约定

- 新建独立项目目录，不复制旧项目的密钥、运行库、任务记录或数据库。
- 不自动启动、停止或修改其他项目服务，不占用正在运行测试的本地模型。
- 首次真实模型连通或集中评测前，列出模型/Embedding 来源、预计调用规模和费用上限；这份规划不是无限费用授权。
- 先做可解释的单条 RAG 链路，不为展示 Agent 而增加多 Agent 编排。
- 阶段完成后更新“已完成/未验证/未完成”；有问题先定位，不用虚构数据补齐验收。
- 通过验收的阶段再进入下一阶段；每个可回退阶段形成 Git 提交，main 保持可运行，功能使用短分支。

## 12. 资料与技术核对来源

技术方案核对日期：2026-10-20。以下为官方资料；实际开始时再核对具体版本、模型和依赖兼容性。

- pgvector：支持 PostgreSQL 内向量存储、精确/近似检索；过滤与 ANN 的组合需要关注召回影响。小数据先使用精确检索的选择基于项目规模，而非必须追求复杂索引。https://github.com/pgvector/pgvector
- PostgreSQL 全文检索概念：用于理解文本解析、索引和查询；不据此声称默认支持高质量中文切词。https://www.postgresql.org/docs/current/textsearch-intro.html
- pypdf 文本提取与局限：扫描件 OCR 不在本期解析范围。https://pypdf.readthedocs.io/en/stable/user/extract-text.html
- Ragas 指标参考：可辅助设计检索与回答评测；本项目先用可解释的自有样本和人工标准，不强制接入全部指标。https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/

本规划的目标是形成一个能解释业务价值、能追溯证据、能复现实验的 RAG 项目。具体技术和门槛可按实际数据修订，修改应保留理由与版本。
